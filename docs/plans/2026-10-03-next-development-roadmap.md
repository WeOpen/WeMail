## 目标与排期假设

下一轮以“邮件到达后，提取可信、通知可恢复、发件状态可解释、自托管可验证”为目标。优先补齐已有能力的业务闭环，继续围绕临时邮箱、验证码/链接提取与自动化集成建立产品优势。

按一名熟悉项目的全栈开发者估算，核心工作约 **22–37 个开发日**；预留联调与环境准备时间，建议安排 **6–9 周**。以下工时是规划估算，阶段一完成后根据实际基线重新估算。第三方账号、测试域名、staging 资源与凭证的准备时间单独计算。

本计划基于本地源码、测试、工作流与文档核对。没有查询线上部署、远端 CI 或真实邮件投递状态；“已有实现”不等于“线上已验收”。

## 阶段一：修复通知缺口，建立验证基线

**优先级：P0；预计 4–6 个开发日；候选版本：0.4.1。**

### DEV-01 聊天渠道重放与内容修复（2–3 日）

源码依据：`apps/worker/src/app/services/webhook-service.ts`。

- 当前 `sendWebhookEventToEndpoint` 将平台渲染后的 `body` 保存为 `payloadJson`，而 `retryWebhookDelivery` 按含 `eventType` 和 `data` 的通用事件解析。聊天渠道请求体不符合该契约，重放可能退化为只有事件标题。
- 同一服务的 `buildChannelText` 只保留字符串值，但入站 `message.extracted` 的 `extraction` 是对象，验证码/链接不会自动进入聊天文本。
- 保存稳定的原始事件与独立的平台请求体；重试读取原始事件，再按目标渠道渲染。兼容旧通用 Webhook 记录，对无法还原的旧聊天记录给出明确错误。
- 将主提取结果、有效期和必要上下文映射为聊天文本；处理长度限制。统一投递超时，并检查平台业务响应，避免仅凭 HTTP 200 判定成功。

验收：五种 Webhook 渠道都覆盖“首次失败 → 手动重试成功”；重试后的主题、发件人和提取值保持完整；原始事件签名契约与旧通用记录继续兼容；无越权重放。

### DEV-02 基线与文档一致性（2–3 日）

- 执行完整 lint/typecheck/test/build 与现有 E2E，记录基线结果、耗时和阻塞项。
- 整理功能状态为“已实现 / 已联调 / 已上线验收”，同步旧成熟度计划和测试目录说明。
- 修正根 README 的旧版本徽章；版本仍以根 `package.json` 为准。
- 核对备份恢复手册：GitHub Actions 的绑定来自 Environment secrets，恢复切库步骤要与此一致；保留手动部署分支说明。
- 核验首页“5 分钟部署”等可测量表述，未获得操作记录支撑的内容改为准确说明。

验收：有可复现的基线报告；现有失败逐项登记并解决本阶段阻断项；文档不存在已删除功能仍被描述为现有入口的情况。

## 阶段二：打通真实邮件业务测试

**优先级：P0；预计 3–5 个开发日；依赖 DEV-02。**

### DEV-03 本地 Worker/D1 业务 E2E

- 新增独立业务 E2E 配置，启动本地 Worker、隔离 D1 和 Web；统一准备邀请码、用户与邮箱数据，测试后清理。
- 覆盖“邀请码注册 → 登录 → 创建邮箱 → 入站处理 → 列表/详情 → 多结果提取 → API Key 读取 → 撤销后拒绝访问”。
- 将生产入站处理函数纳入受控测试驱动；生产 API 不增加公开测试投递入口。外部邮件供应商用可控适配器，明确测试边界。
- 覆盖跨用户邮箱访问拒绝、scope 拒绝、额度耗尽、重复 Message-ID、HTML 邮件、附件与失败重试。
- CI 单独运行业务 E2E，失败上传日志与浏览器产物；保留当前模拟 API 的快速页面测试。
- 为 staging 列出真实 Email Routing、Resend、聊天平台的验收步骤与证据模板。

验收：本地可用一条命令运行核心业务测试，CI 可重复通过；权限、幂等和失败路径有断言；报告明确哪些外部链路仍需 staging 验收。

## 阶段三：通知可恢复与可观察

**优先级：P1；预计 5–8 个开发日；依赖 DEV-01、DEV-03；候选版本：0.5.0。**

### DEV-04 持久化通知事件与投递任务

源码依据：`apps/worker/src/app/runtime.ts` 在邮件保存后逐项发送通知；重复邮件被抑制后直接返回。由此推断，保存成功后通知阶段发生中断时，重投邮件不能保证补齐通知，需要故障注入验证。

- 设计并记录消息落库与通知事件持久化的一致性边界；以 D1 outbox 作为可恢复事件源，评估 Cron 扫描与 Cloudflare Queues 的成本和部署要求后定案。
- 投递任务增加状态、尝试次数、下次执行时间、最后错误和稳定事件 ID；以消息、事件类型、目标建立唯一任务约束。
- 支持指数退避、最大尝试次数、可重试错误分类、失败终态和手动重放；HTTP 429 尊重合理的 Retry-After。
- 将“事件 ID”与“单次尝试 ID”分开，方便接收方去重。外部调用采用至少一次投递语义，不承诺不可实现的端到端 exactly-once。
- 入站保存成功后，某个通知目标失败不阻塞其他目标；敏感验证码和原始邮件内容沿用保留策略，避免投递记录无限累积。

验收：通知期间模拟中断后可恢复；重复投递不生成重复任务；最终失败可见、可重放；队列/扫描故障不会导致邮件丢失。

### DEV-05 投递状态与规则可解释性

- 在现有 Webhook/Telegram 与系统设置页面展示待投递、重试中、失败终态、最近成功和积压信息。
- 为通知免打扰规则明确时区，支持跨午夜；兼容既有 UTC 规则并说明迁移方式。
- 增加规则测试结果：是否匹配、命中了哪些条件、为何被免打扰规则抑制。

验收：用户能定位“为何没收到通知”并采取操作；待处理计数与数据库任务状态一致；权限遵循现有用户/管理员边界。

## 阶段四：发件执行与状态闭环

**优先级：P1；预计 4–7 个开发日；依赖 DEV-03、DEV-04 的任务模型；候选版本：0.6.0 的一部分。**

### DEV-06 重试执行、幂等与最终状态

源码依据：`apps/worker/src/app/use-cases/outbound-use-cases.ts` 的 `sendEmailWithRetries` 当前立即循环；`retryDelay` 出现在摘要，未进入执行逻辑；发件记录状态是 `sent`/`failed`。

- 将重试间隔转换为执行规则，明确首次发送与后台重试的边界；永久错误不重复发送。
- 增加稳定的发送请求标识，核对供应商幂等接口；覆盖供应商已接收但本地超时的情形，避免重复邮件。
- 明确额度按尝试还是逻辑请求计费、失败如何处理；保证并发下限额一致，重试不会意外重复扣减。
- 接入供应商投递事件前，核对官方验签与事件契约；新增 accepted/delivered/bounced/complained 等状态，兼容旧 `sent` 记录。
- UI 显示状态时间线、错误原因与可重试操作。单独标注静态配置检查和真实 DNS/供应商检查的来源、检查时间及结果。

验收：配置的等待间隔实际生效；同一请求不会因自动重试重复扣额；供应商事件可验签、可去重、可处理乱序；前端准确区分已受理与已送达。

## 阶段五：提升提取质量和首次使用成功率

**优先级：P1/P2；预计 4–7 个开发日；依赖 DEV-03，可按小批次交付。**

### DEV-07 提取质量评估（2–4 日）

- 建立至少 50 封去敏邮件样本，覆盖中英文、多个验证码、多个链接、转发、订阅退订、有效期、钓鱼样式、价格/日期误识别与异常格式。
- 固定精确率、召回率和主要误识别类型的基线；规则优先、AI fallback 单独评估成本与错误。
- 改善多结果的选择/复制、缺少有效期和发件认证未知状态的提示。
- 核对 Authentication-Results 的信任来源，区分可信上游结论与未经验证的邮件头，避免认证徽章误导用户。

验收：新增规则必须通过固定样本回归；价格/日期等重点负样本不误判；质量改进有前后比较数据；界面不将“未知”呈现为“安全”。

### DEV-08 首次使用与自托管检查（2–3 日）

- 串起“创建首个邮箱 → 说明如何发送测试邮件 → 确认收到 → 复制提取结果 → 可选通知”的引导。
- 复用已有系统诊断，提供域名/Email Routing、密钥、功能开关、清理任务配置的检查说明与修复入口。
- 补充三条任务导向文档：用 API 取验证码、推送聊天平台、独立域名自托管。

验收：新用户能完成首封邮件流程；未配置能力提供具体下一步；诊断结论区分配置存在与真实服务可用。

## 阶段六：发布验收

**优先级：P0 发布门槛；累计预计 2–4 个开发日，按每次候选发布分摊。**

- 每个开发批次都更新根 CHANGELOG；只有实际切版时才修改根版本并同步 workspace、共享常量与 OpenAPI。
- 每次候选发布执行：`pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build`、`pnpm version:check`、`pnpm api-catalog:check`、迁移编号检查、`pnpm preflight` 与相关 E2E。
- 新迁移必须验证“空库初始化”和“旧版本升级”；涉及事件/任务结构时验证旧投递记录与未完成任务兼容性。
- staging 验证真实收件、重复投递、附件、提取、通知重试、发件及权限边界，并保存记录。
- 对计划发布的 schema 变更演练备份/恢复与旧代码兼容性，明确代码回滚和数据恢复的不同路径。
- 满足部署手册门槛后再安排 production；发布后按手册观察错误、积压、重复发送和清理失败。

验收：本地与 CI 必要检查通过；staging 核心链路有证据；迁移、旧数据兼容和回滚路径明确；新增 P0/P1 问题关闭。
