---
title: 推送聊天平台
description: 绑定 Telegram 或聊天 Webhook，验证首条消息并排查通知重试
---

目标：邮件到达后，在自己的聊天中收到一次包含提取结果的通知。先完成真实收件，再接通知，便于确定故障发生在哪一段。

## Telegram

1. 管理员在 Worker Secrets 配置 `TELEGRAM_BOT_TOKEN`。staging/production 还需要 `TELEGRAM_WEBHOOK_SECRET`；可配置 `TELEGRAM_BOT_USERNAME` 生成直达链接。
2. 在「系统设置」确认 Telegram 功能已启用。进入「Telegram」，由管理员配置 Webhook 和 Bot 菜单。
3. 每位用户在自己的 Telegram 设置页生成绑定码，打开对应 Bot 并完成绑定。绑定码不能发给其他人。
4. 启用自己的订阅，点击发送测试消息。页面显示绑定或密钥存在，只能证明配置存在；以聊天实际收到测试消息为准。
5. 从外部邮箱发送带验证码的新邮件，确认聊天收到通知，并与「投递状态」中同一事件的结果核对。

## Slack、Discord、飞书、企业微信

1. 在聊天平台创建传入 Webhook，复制平台给出的完整 URL。URL 带有授权凭据，应按密钥保存。
2. 打开 WeMail「Webhook」，新增端点，选择准确的平台渠道；普通 `webhook` 使用通用 JSON 格式，不能替代聊天平台渠道。
3. 选择 `message.received`；如只需要已提取邮件，可按业务需求选择 `message.extracted`。同时订阅两种事件可能按设计收到两条通知。
4. 保存并执行测试。确认聊天实际显示验证码或链接，不能仅凭 HTTP 200 判断业务成功。
5. 在通知规则中限定邮箱、关键词或提取类型。先运行规则测试，检查匹配与抑制原因，再发送一封新邮件验证。

免打扰时间使用保存的 IANA 时区，旧规则默认 UTC。跨午夜窗口也会抑制通知；测试规则不会实际发送聊天消息。

## 失败时逐层检查

| 现象 | 检查与修复 |
| --- | --- |
| 收件箱里没有邮件 | 先按 [Email Routing](/docs/email-routing) 验证路由和地址 |
| 收到邮件但没有任务 | 确认端点/订阅启用、事件类型匹配，查看规则测试中的抑制原因 |
| 等待重试 | 查看下次尝试时间；每分钟 Cron 恢复持久化任务，无需反复点击重放 |
| 暂停 / suppressed | 修复关闭的端点、订阅或规则条件后再重放允许恢复的任务 |
| 失败 | 查看平台响应、密钥、URL 和权限；修复后在投递状态重放一次 |

通知自动重试最多五次。手动重放会开启新一轮尝试，应先确认聊天中是否已经收到，避免人为重复通知。超过邮件保留期的事件不能按原内容继续投递。

完成标志：真实邮件进入收件箱，聊天中收到对应事件，页面显示投递成功；中途断网后，任务能由调度恢复。部署侧验证见[自有域名部署](/docs/self-hosted-domain)。
